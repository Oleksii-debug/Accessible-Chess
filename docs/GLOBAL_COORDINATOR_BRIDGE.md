# Global Coordinator Bridge

Accessible Chess participates in the owner's cross-project autonomous development control plane.

## Purpose

Workers, Codex Cloud and Work must not rely on stale prompt text as the current project plan. Before substantive work, reconstruct the newest Accessible Chess state and read current coordination surfaces. The coordinator updates shared priorities; Oleksii should not need to manually rewrite worker prompts after each external development run.

## Coordination hierarchy

1. Global coordinator master: cross-project priorities for Nika Core, 12-6 AI, Accessible Chess and future projects.
2. Project-local plan: current Accessible Chess priority, completed work, do-not-repeat items, active ownership and next unowned packages.
3. Worker execution: each run takes only current useful work and leaves durable evidence.

## Audit cadence

When Accessible Chess is actively developed, use periodic audits and refresh after major changes. When paused, do not consume scarce automation capacity simply to report no change. The global coordinator may keep the project in low-frequency/paused monitoring until Oleksii reactivates development.

## Current owner priority

When active, prioritize the user-visible formats/books path and a genuinely usable accessible release. Avoid diverting scarce Nika Core / 12-6 AI development capacity into inactive Accessible Chess work unless the global coordinator or Oleksii explicitly raises its priority.

## Owner-facing reporting

Oleksii is not expected to manage GitHub mechanics. Reports should use plain Ukrainian: what is ready, what works, what does not work yet, what changed, current readiness and the next user-visible milestone.


# Format Factory and chess Braille Factory — ACTIVE engineering scope

The owner has explicitly activated **Sections 54 and 55** in the single canonical Google Drive plan. Both are **ACTIVE / OWNER-AUTHORIZED / IMPLEMENTATION OPEN / NOT DONE**. Engineering work may begin now in specifically assigned, independent workers with scoped PRs, tests, integration and qualification. These parallel workstreams do not block acceptance or shipping of mandatory Sections 0–53 and do not authorize changes to protected finished core work.

This is a technical design companion, **not a second numbered plan**. Section clauses below mirror the canonical Drive plan. Active status does not imply that either factory has already been implemented. Paid external calls, transmission of private books and physical printer use still require configured consent, keys, source rights and explicit per-run INPUT/OUTPUT token limits. No mandatory monthly or currency budgets.

## Current-source technical reuse boundaries (owner-authorized engineering)

- `acs/bookdocument.py`: current semantic blocks; **never** change accepted semantics simply to accommodate a new importer. Proposed metadata/provenance extensions must be additive and migrate safely.
- `acs/bookreader.py`, `acs/book_board_workflow.py`, `acs/book_game_content.py`: book navigation, Board/GameTree session, FEN and legal-move authority; no AI or PDF parser may create competing chess truth.
- `acs/version2_book_workspace.py`, `acs/version2_windows_book_board_adapter.py`, `web/full_product_books_training.js`: book-to-board accessible presentation, actions and restoration; reusing them does not automatically imply finished Section 54.
- `acs/pgn_workspace.py`, `acs/pgn_document.py`, `acs/book_library_import.py`: PGN/game ingest is currently separate from book reading. A future conversion must preserve this distinction and create a tested bridge, not pretend plain PGN is already a pageable book.
- `acs/book_epub_import.py`, `acs/book_html_import.py`, `acs/book_text_import.py`, `acs/library_import_service.py`: existing format readers; support for PDF, DOCX, scanning and some proprietary formats is **future work**, not an already-qualified capability.
- `acs/ai_provider_gateway.py` and existing Agent routing: reuse one consent/security/model routing boundary; external web lookup must be explicitly policy-gated, never silently reveal a private document.
- Existing Windows/Web accessibility, durable persistence, Library/ACSDB import/export, crash and restart infrastructure retain their owners. Any new job service is an adapter/application orchestration layer, not another chess parser.

## Proposed typed conceptual contracts (not shipped APIs)

**FormatFactoryJobPolicy**: source_id/source_sha, user_id, intended_source_edition, sections/pages/positions/games selector, selected output formats, output language, source-search permissions, provider/model selection, semantic confidence policy, per-run input_token_limit and output_token_limit, queue-priority, sequential/parallel eligibility, error policy, consent version, provider usage report version. Missing model quotas must produce an explicit non-paid preflight or require policy; no invisible default monetary budget.

**FactoryJobState**: READY -> RUNNING -> PAUSED_LIMIT | PAUSED_USER | UNVERIFIED | FAILED_RECOVERABLE | COMPLETED; terminal success only if requested scope passes. Every job has a source version, an immutable policy snapshot, idempotent fragment checkpoint and an append-only per-provider token-use ledger. A single book can have multiple distinct selected fragment targets and output targets, each with independently resumable acknowledgements.

**FragmentEvidence**: origin title/edition/language, source page and physical page, source hash, exact visual/text anchor, extracted text and block identity, optional FEN/GameTree cursor/authorial moves, alternative-source URL and license, detection method/model, deterministic legality result, unresolved flags, acceptance status and quality-validator version. Never store fabricated chess positions as accepted.

**BrailleProductionProfile**: checked language/grade/table hash/chess notation, embossing device/driver, page geometry, paper, cell dimensions, volume split, tactile legend, output formats and capability matrix. Output must declare what has actually been measured/validated for that profile, not generic compatibility.

**Publication contract**: write atomically to a new destination after content, rights, output-format and post-conversion QA; preserve original unchanged. Export manifest lists losses, unresolved, unknown, external citations, checksum, checkpoint, profile and applicable provider usage. No successful print-ready flag if any required proof is absent.

## Quality and acceptance strategy

1. Prioritize deterministic parsing, source-aware reading, bounded local OCR and official chess engines; only then use metered LLM/vision with a declared provider. Preserve source over AI guesswork.
2. Run canonical legality checks for each rooted game/variation and independently compare every reconstructed diagram/text description to its source page. For semantically different versions of the same edition, require reconciliation or preserve an unresolved flag.
3. Prove resumability and zero duplicate successful fragment processing through crash-injection, interrupted source read, rate-limit, timeouts, concurrency, repeated enqueue, source mutation and output failure tests.
4. Token envelopes: preflight prompt/model/reserved response, actual provider-reported input/output/cached/reasoning tokens where reported, retries and fallbacks; gate next request on remaining input/output limits. Do not promise hard sub-request stop if the provider cannot enforce it; fail closed for such a requirement.
5. No source transmittal to an unapproved external API, no paid inference without user-configured consent, credentials and per-run input/output token limits, no live search beyond consent/rights boundaries, and no unauthorized redistribution of source or derivative outputs.
6. Validate tagged PDF reading order, semantic EPUB3, actual PGN variation fidelity, keyboard/NVDA, book/game/Board return path, provenance report and real representative content for the declared supported matrix.
7. For Braille, validate translator tables and chess-specific notation with independent references; render and check every output page/profile, automated diagnostics for unsupported tactile graphics, then validate actual embossed output on an allowed physical-device qualification matrix. Expert human evaluation establishes/updates the acceptance evidence for the SYSTEM, but the goal is automatic per-job print-ready without mandatory manual editing only within proven classes of books.
8. Novelty and performance claims require independent benchmark and qualified corpus. An internal synthetic green run alone is insufficient.
9. Unimplemented capabilities and untested printer models remain UNSUPPORTED or UNVERIFIED. The two sections are ACTIVE and their detailed requirements now bind assigned engineering work, without retroactively delaying Section 53 closure.

## Activated workstreams, ownership and baseline boundary

- **ACTIVATED:** Owner authorizes scoped work on both Sections 54 and 55 now; no further explicit command is required to begin design, coding, testing, and integration within those scopes. Neither is DONE.
- **Worker assignment:** A 54 worker owns Format Factory orchestration and conversions; a 55 worker owns chess Braille production. They may work in parallel where ownership is disjoint; shared files and dependencies require coordinated exact-SHA convergence and reuse.
- **Baseline:** The ordinary sequential worker still selects 0–53, and completion of 0–53 is sufficient for the base release. Active 54/55 work does not reopen or block any DONE or required baseline Section.
- **External calls:** Provider billing, online source upload, physical printer operation or distribution require user-controlled credentials, lawful source permissions, per-run token limits, and suitable devices. Activation alone is not a blanket authorization for these actions.
- **Market:** Chess publishing remains primary for 55; compatibility with generic books is acceptable. User/customer interviews or institutional pilots require separate participant consent and practical arrangements.

# SECTION 54 — Інтелектуальна Фабрика форматів і доступних шахових книг (ACTIVE / РОЗРОБКУ ДОЗВОЛЕНО; ДОПОВНЮЄ ОСНОВНИЙ ПРОДУКТ)

Статус: ACTIVE / OWNER-AUTHORIZED / IMPLEMENTATION OPEN / NOT DONE. Власник прямо активував Section 54. Дозволено вже зараз планувати й реалізовувати функцію, вести цільові PR, тести, інтеграцію та кваліфікацію; спеціально призначені воркери можуть працювати паралельно з базовим продуктом без перетину ownership. Базові Sections 0–53 залишаються обов'язковою умовою релізу, а 54 не блокує їхній DONE і не відкриває їх повторно. Платні API-запуски лише за налаштованими дозволами, ключами й лімітами INPUT/OUTPUT токенів на запуск. Активний статус означає дозвіл на розробку, а не завершену функціональність.

Мета і користувацький результат: одна надана шахова книга або збірка в будь-якому заявленому вхідному форматі → автоматичне відновлення її точного змісту, шахової семантики й доступної структури → один чи декілька обраних цільових форматів. Користувач не мусить сам знаходити багато видань, програмувати, виправляти OCR чи вручну вводити ходи. Не обіцяти підтримку невідомого формату до перевірки його реального декодера; не вигадувати позиції або авторський текст.

Залежності на момент майбутньої активації: використовувати існуючі BookDocument, BookReader, Book/Library ingress, PGN/GameTree, canonical Chess Core/Board, Stockfish, AI Agent/ModelGateway, Windows/Web/NVDA, persistence, packaging. REUSE → REPAIR → CONVERGE; жодного другого шахового рушія, PGN-парсера, конкуруючого book schema чи повторної реалізації завершеного продукту.

## Підрозділи

- **54.1.** Вхідна книга, походження і метадані. Користувач передає ОДИН доступний файл (можна добровільно додати інші): PGN, EPUB, DOCX, HTML, TXT, Markdown, текстовий або сканований PDF, зображення, ZIP, підтримувані ChessBase/базові формати. Автоматично розпізнати тип за байтами, відмінності видання, назву, автора, мову, дату/рік лише коли це доказово підтверджено, зміст, ієрархію глав, розвороти та прив’язку надрукованих сторінок до сторінок файла. Відрізняти підтримуваний імпорт, частковий імпорт і несумісне джерело; оригінал не змінювати.

- **54.2.** Внутрішнє семантичне представлення. Перевести зміст у розширення чинного BookDocument: title/author/edition/language, headings/chapters/paragraphs/lists/notes/tables/images, source page/anchor, Game/VariationTree/Position/Diagram/Exercise, FEN/PGN, коментар, граф альтернатив, логічні зв’язки та confidence/provenance. Зберегти порядок читання, авторську форму, нумерацію і відмінність головної лінії від варіацій; коректно представляти дубльовані й відсутні елементи. Для кожного результату тримати source reference та versioned checksum.

- **54.3.** Автоматичне розпізнавання та мультимодальний агент. Спочатку застосовувати дешеві безмодельні імпортери, OCR/зображення тільки де потрібно, потім виклики дозволених API-моделей для неоднозначних шахових діаграм, записів ходів, мовного тексту, таблиць, багатоколонкових сторінок. Виявляти змішані мови, багатотомність, вихідні позиції не зі стандартного початку та Chess960. Ніколи не маскувати непевність моделлю «усе готово».

- **54.4.** Шахова формальна кваліфікація. Агент може використовувати інструменти реальної шахівниці й canonical Board/GameTree, відтворювати кожен mainline і branch із коректного стартового FEN; перевіряти легальність ходів і зіставлення діаграм із текстом. Stockfish — додаткова аналітична перевірка, а НЕ доказ того, що так написав автор. Для неузгодженостей встановлювати source-anchored NOT_PROVEN/CONFLICT, не «виправляти» книгу вигаданими ходами; не публікувати недостовірну шахову позицію як валідну.

- **54.5.** Автономний дозвільний пошук допоміжних джерел. Якщо надане видання нечітке, агент сам ідентифікує твір і за попередньо заданою політикою може шукати законно доступні публічні сторінки, PGN, бібліографію або інше видання; із користувацьким підключенням — його ліцензовані бібліотеки. Перевіряти збіг автора, року, видання, структури, партії та source anchors; розбіжності версій позначати. Додаткові матеріали тільки corroboration, а не підміна користувацького оригіналу. Не завантажувати піратські копії, не обходити paywall/DRM, не відправляти приватну книгу пошуковим сервісам без дозволу та не поширювати її повний текст у відкритих логах.

- **54.6.** Чат і природномовні інструкції. Нативно підтримати «повністю всю книгу», «лише глава 3», «сторінки 12–38», «до сторінки 60», «позиції 5–24», «всі діаграми», «перші 20 партій», «онови тільки непідтверджені місця», «додай наступну главу», «створи доступний EPUB/PDF/PGN». Чат перетворює запит на явну перевірювану політику, яку користувач може відкрити, змінити і затвердити перед дорогим запуском. Не перепитувати те, що політика вже визначає.

- **54.7.** Безчатива доступна форма налаштувань. Доступний NVDA/keyboard/Web UI з прапорцями і текстовими полями: ціла книга/глави/сторінки/діаграми/позиції/партії, список конкретних діапазонів, мова виходу, вихідні формати, пошук джерел, provider/model, OCR і рівень перевірки, подальша поведінка при помилці. Підтримати кілька несуцільних діапазонів та коректні друковані/файлові номери сторінок. Контроль має бути можливий без миші й без знання промптів.

- **54.8.** Вихідні представлення і чесність конверсії. Видавати залежно від обраного виходу доступний tagged PDF із семантичним порядком читання й описами шахових діаграм, EPUB3, DOCX, HTML, TXT/Markdown, PGN із партіями/варіантами/коментарями, а також внутрішню книгу/ACSDB при дозволеному форматі. Враховувати, що PGN не зберігає повністю візуальну верстку та довгі нехудожні розділи; при втраті семантики створювати manifest втрат або комплементарну пару (напр., EPUB + PGN), ніколи не заявляти безвтратність помилково. Підтримувати preview, ідентичність видачі й перевірку фінального файла.

- **54.9.** Список книг, довготривале збереження і відновлення. Кожна книга має власний запис: source fingerprint, назва, обрана політика, target formats, які глави/позиції опрацьовано, які не перевірено, versioned checkpoints, API usage, повтори, готові outputs, owner permissions, audit trail. Продовжувати частинами через дні/тижні, без перекодування вже доказово незмінних фрагментів. Операції скасування/перезапуску/зміни формату не руйнують source або прийняті results; відновлення після power/network/provider failures і перевірка цілісності.

- **54.10.** Черга і паралельна обробка. Застосувати глобальну користувацьку чергу книг та незалежну політику на кожну: повна книга або обмежена частина, вихідні формати, пріоритет, послідовний або обмежено паралельний запуск, повтори/відкладення, provider routing, source/search permissions, статуси WAITING/RUNNING/PAUSED/REVIEW_REQUIRED/DONE/PARTIAL/FAILED. Жодна книга не змінює політику іншої. Зберігати leases, heartbeat, ідемпотентність, crash recovery та контроль 429/timeouts; за бажанням перейти до наступної книги після зупинки попередньої.

- **54.11.** ВИКЛЮЧНО токенові ліміти одного запуску, без грошових/місячних бюджетів. Користувач явно задає max INPUT tokens і max OUTPUT tokens для конкретного запуску (та за бажанням додатково per-model/per-operation limits), бачить usage by model, aggregate, cached/uncached та залишок. Система перед кожним платним викликом резервує обмежений token envelope, перевіряє provider max_output_tokens/аналог і враховує retry, tools, OCR multimodal metering та internal reasoning, де API повідомляє це. При досягненні будь-якого обраного ліміту зупинити відповідне завдання, зберегти checkpoint і показати межу; виклики без технічної можливості виконати hard stop мають fail-closed або чесно зазначати неможливість абсолютної гарантії під час in-flight request. Не вводити обов’язкових EUR/USD/price/money-budget параметрів.

- **54.12.** Стани перевірки й автономний контроль якості. Фіксувати розбіжності OCR, мови, позиції, прав книги, edition mapping, сирі/відновлені FEN, round-trip/semantic-diff, перевірені й невирішені сторінки; автоматично порівнювати вихід зі структурною і контентною моделлю й при потребі повертатися на мінімальний проблемний фрагмент. Fail closed: incomplete source, illegal moves, misaligned source, source drift, interrupted job, unlicensed external copy чи перевищення токенів не публікують «повністю готову» книгу.

- **54.13.** Доступність, безпека, приватність. Діалоги і прогрес для NVDA й keyboard; live announcements без надмірних повторів; правильний фокус після черги й помилки; прозорий consent для зовнішніх API, мінімізація переданих сторінок, секрети тільки захищеним каналом, видалення кешів за політикою; без автоматичного публічного розповсюдження приватних/авторських книг. Урахувати юрисдикцію й винятки для створення доступних примірників, не трактуючи їх як універсальну ліцензію.

- **54.14.** Реальні тести й performance/acceptance. Кваліфікувати мінімум чистий PGN із варіаціями, структурований EPUB/HTML, DOCX, TXT/Markdown, текстовий PDF, сканований PDF із діаграмами, вихід не зі стартової позиції, реальні багатомовні глави та великі книги. Тести для незаконних ходів, хибних FEN, неправильно ідентифікованих видань, несумісних ChessBase, відсутнього інтернету, 401/429/timeouts, token-stop, parallel races, зміни файла, повного restart, NVDA, доступного PDF/EPUB та незворотних втрат PGN. Для незаявленого формату явно UNSUPPORTED/PARTIAL. Порівняти з матеріалами історичного 39-book Drive workflow як тестовою методикою лише за правомірного доступу; жодна з 39 книг не вважається завершеним фабричним еталоном автоматично.

- **54.15.** Кінцевий DONE і незалежність від основної програми. ACTIVE / IMPLEMENTATION OPEN: виконання дозволено зараз, але DONE лише після інтеграції доступної користувацької функції у фактичну Windows/Web збірку, реальних наскрізних тестів і durable evidence на точному main SHA; PR/коміт/один зелений тест не є DONE. Не вимагати Section 55 і не змінювати shipping gates Sections 0–53. Повторно використовувати наявні модулі без дублювання або руйнування завершеної роботи.

# SECTION 55 — Автоматизована фабрика шахових видань Брайлем для професійного друку й цифрового читання (ACTIVE / РОЗРОБКУ ДОЗВОЛЕНО; ДОПОВНЮЄ ОСНОВНИЙ ПРОДУКТ)

Статус: ACTIVE / OWNER-AUTHORIZED / IMPLEMENTATION OPEN / NOT DONE. Власник прямо активував Section 55 як окремий паралельний напрям розробки фабрики Брайля саме для шахової літератури. Дозволено вже зараз вести спеціально призначені роботи, технічну реалізацію, PR, прототипи, тести й кваліфікацію за вимогами цього плану. Це не умова випуску Sections 0–53 і не причина переписувати завершені компоненти. Дозволені лише погоджені підключення провайдерів і токенові ліміти на запуск, без автоматичного платного друку чи передачі приватного змісту. Опитування ринку й реальні експертні пілоти узгоджуються окремо. ACTIVE не дорівнює DONE.

Продуктовий фокус: ПЕРШОЧЕРГОВО шахова література (позиції, діаграми, партії, варіанти, шахова нотація, вправи й коментарі); технічна придатність трансляційного ядра до звичайних книг допустима як побічна універсальність, але не створює обов’язку розширювати продукт на світове загальне книговидання чи робити звичайні книги пріоритетом. Замовник: шахова бібліотека, брайлівська друкарня, школа, реабілітаційний/навчальний центр чи організація незрячих.

Цільовий результат: організація надає одну шахову книгу, обирає брайлівський стандарт і мовну таблицю, профіль конкретного embosser/дисплея, тип носія та режим, а фабрика автономно готує професійно оформлений output для БЕЗПОСЕРЕДНЬОГО друку/читання, включно з точними шаховими позиціями. Не обіцяти нуль помилок для довільних непідтверджених джерел: «готово до друку без ручного доопрацювання» — тільки результат доведеного автоматичного qualification gate. Апаратні дефекти/якість фізичної рельєфної крапки відокремлено від правильності файла.

Залежності при майбутній активації: застосувати результати й модулі 54, якщо Section 54 уже активовано й реалізовано; або існуючий Books/Board/GameTree/Library/AI Agent/Export boundary, якщо 54 не активовано. Технічно окремий опціональний plugin/module, без зміни chess core, main shipping plan і без дублювання parser, OCR чи BookDocument. Відсутність 54 не блокує Section 55 як план, поки він не активований.

## Підрозділи

- **55.1.** Стандарти й мовні профілі. Конфігурований вибір мови та стандарту Брайля (наприклад, UEB, відповідні українські/німецькі/інші таблиці, повний або скорочений запис, спеціалізована шахова нотація, математика де є). Трансляція через перевірене правило-орієнтоване ядро (наприклад, Liblouis або сумісний перевірений механізм); ШІ допомагає зрозуміти контекст, але не замінює формальний кодувальник. Version/hash кожної таблиці та профілю є частиною output provenance.

- **55.2.** Самостійне отримання і відновлення книги. Організація передає ОДНЕ видання в наявному форматі; система автоматично ідентифікує зміст, OCR, заголовки, примітки, шахові діаграми, таблиці та схему глав. Допоміжне пошукове зіставлення законних джерел за тією ж explicit permission політикою, що й 54. Права/конфіденційність/видання мають бути доведені, зміни між виданнями не змішувати мовчки.

- **55.3.** Шахова семантика. Для всіх діаграм, партій і гілок зберігати canonical FEN, фактичну сторону ходу, шахові фігури, ходи, джерело й структурний зв’язок із текстом; Board/GameTree підтверджує легальність, Stockfish допомагає аналізувати, але не переписує авторську думку. Якщо позиція не може бути доведена — статус NOT_PROVEN, а не вигаданий коректний FEN.

- **55.4.** Брайлівське представлення шахів. Підтримати стандартизовані шахові скорочення/позначення вибраної мови, список фігур за полями, хід/сторона/номер ходу, головні та бічні варіанти, позначки оцінки та вправи з рішеннями. Для кожного обраного виду зберегти еквівалентні значення й стабільний зв’язок із GameTree; синхронізувати розташування позиції у тексті, Брайлі та на звичайній шахівниці.

- **55.5.** Текстова і тактильна графіка. Для діаграми сформувати читабельний семантичний опис та, коли заявлено, спеціально спроєктовану рельєфну шахову діаграму з контуром, символами, орієнтацією, легендою, тактильною роздільною здатністю й мінімальними відступами. Не друкувати автоматичну «рельєфну копію картинки» без моделі сприйняття; тактильний output перевіряти за профілем друкарні й відповідними рекомендаціями.

- **55.6.** Типи результатів. Випускати BRF для узгоджених принтерів/брайлівських дисплеїв, PEF для сторінкового archiving/embossing і eBraille/eBRL (за реальною перевіреною підтримкою стандарту й читачів). За потреби доступний EPUB3/HTML для NVDA та синхронізованих refreshable braille displays. Підтримка форматів не означає, що будь-який дисплей читає всі з них: повідомляти про сумісність конкретного пристрою.

- **55.7.** Профілі реального обладнання й верстка. Перед стартом організація обирає embosser model/driver, одно-/двобічний друк, кількість клітинок у рядку, рядків на сторінці, розмір/тип паперу, міжряддя, довжину томів, титульні сторінки, зміст, закладки, нумерацію друкованих/брайлівських сторінок і layout constraints. Генерувати профіль-специфічний друкарський файл та чіткий список параметрів printer setup; не заявляти «готовий для цього пристрою», поки профіль і sample output не кваліфіковано.

- **55.8.** Повністю автономний виробничий цикл. В одному завданні: source intake → OCR/структура → реконструкція шахової семантики → перевірка авторського тексту/позицій → formal braille translation → розбиття на сторінки й томи → независима автоматична валідація → точковий repair loop → повторна валідація → signed output manifest → готові print/read bundles. Ніякого обов’язкового набору речень або ручного редагування за замовчуванням. Якщо докази недостатні, не приховувати цю обставину й не примушувати до друку.

- **55.9.** Автоматичне приймання print-ready. Валідатори перевіряють коректність і версію таблиці Брайля, знаки/спецпозначення, баланс сторінок, line wrap, volumes, друкарський профіль, відповідність усіх розділів оригіналу, точний шаховий контент, структуру діаграм, цілісність даних і відсутність пропусків. Додатково незалежний round-trip/backtranslation/structural comparison там, де це коректно. Статуси: PRINT_READY_AUTOMATICALLY_VERIFIED, RETRY_OR_REPAIR, UNVERIFIED_REQUIRES_DECISION; останній не є «готовий до друку». Жодний автономний валідатор не є гарантією абсолютної безпомилковості у всіх книгах.

- **55.10.** Читання та синхронізація. Сумісні брайлівські дисплеї й NVDA можуть читати доступний текст і переходити по headings/paragraphs/games/positions. Синхронізація: курсор або навігаційний anchor книги ↔ BookReader ↔ Board/GameTree ↔ мова/голос/Брайль; перехід до відповідної шахової позиції з точним FEN і повернення в той самий абзац. Для багаторядкових тактильних дисплеїв підтримка реальної графіки тільки після перевірки їх API; звичайний однорядковий дисплей показує текстову шахову нотацію.

- **55.11.** Пакет для організації. Один готовий пакет: файли BRF/PEF/eBRL за запитаним форматом, документи керування друком і комплектація томів, обраний language/grade/device profile, читацькі інструкції, структура книги й навігація, source/rights manifest, SHA-256, quality-report, автоматично перевірені й неоднозначні елементи. Видавати output через доступний Windows/Web інтерфейс, із доступним log та експортом у сховище замовника.

- **55.12.** Політика прав, охорона контенту і приватність. Наявність Марракеського договору/винятків для доступних примірників не дає необмеженого права на будь-яке цифрове джерело чи загальну роздачу. Розділ призначено переважно для шахової літератури, наданої правомірно; інституційні права/ліцензії, цільова група та можливість друку/розповсюдження перевіряються відповідно до юрисдикції. Зовнішні API використовувати тільки за політикою згоди; не зберігати ключі й приватні твори у GitHub або загальних логах.

- **55.13.** Керування токенами і чергою. За потреби повторно використати механізм 54: користувач задає max INPUT і max OUTPUT токенів на запуск, не бюджет у грошах і не місячні суми. Batch/queue для багатьох видань із власним друкарським/мовним профілем, checkpoints, керування паралельністю, pause/resume, fail-closed та 429/retry; hard-stop і облік невідомої внутрішньої token usage — як у 54.

- **55.14.** Незалежна промислова кваліфікація. До будь-якої заяви про прорив — тестова матриця реальних законних шахових книг, мов, варіантів нотації, багатоколонкових сканів, дрібних діаграм, великих багатотомних видань і різних брайлівських пристроїв. Сліпі/зрячі профільні читачі та сертифіковані спеціалісти використовуються для НЕЗАЛЕЖНОЇ оцінки системи й еталонів, не як обов’язкова ручна стадія кожного штатного виробничого завдання. Порівняти з професійним workflow: критичні помилки, частка output без людських виправлень, повнота, тактильна зрозумілість, час, придатність до друку, recovery. Не стверджувати «краще за світ» або «нуль ручної перевірки» без доказів і без дозволеного scope.

- **55.15.** Поступова придатність і конкурентна перевага. Першим професійним цільовим класом є ШАХОВА книга з технічно перевіреними позиціями; звичайні книги допускаються через спільний текстово-брайлівський двигун, але вихід за шаховий ринок/загальне книговидання відкладено до подальшого дослідження та рішення власника. Підготувати згодом окрему програму інтерв’ю/опитувань бібліотек і друкарень, але не ініціювати її автоматично.

- **55.16.** Критерій кінцевого DONE. ACTIVE / IMPLEMENTATION OPEN: реалізація дозволена зараз; DONE після фактичної інтеграції в платформу, end-to-end виготовлення з однієї наданої шахової книги, багаторівневих автоматичних quality gates, перевіреного print-ready пакета для заявлених профілів обладнання, доступного цифрового читання Брайлем, незалежних regression/performance/legal/privacy тестів і live readback GitHub. Якщо конкретний PDF, мова або принтер не кваліфіковані — чесно PARTIAL/UNSUPPORTED/UNVERIFIED; не маркувати фабрику DONE без доказів. Section 55 не блокує реліз базових 0–53.
